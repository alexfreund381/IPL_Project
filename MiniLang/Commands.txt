1. BUILD
--------
Rebuild only after changing a .cpp or .hpp file (editing a .mini file
does not need a rebuild):
    cmake --build build

build/ is CMake's output folder. It holds:
    CMakeCache.txt, Makefile, CMakeFiles/  - CMake's build notes
    libmini_compiler.a                     - the compiler code as a library
    minic.exe                              - the compiler itself

First-time setup only (if build/ does not exist):
    cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug


2. MINIC COMMANDS
-----------------
Pattern:   .\build\minic.exe <command> <file.mini>

Each command runs the compiler up to one stage and shows the result:

    tokens   lexer (lexer.cpp)      list of tokens
    ast      parser (parser.cpp)    the syntax tree
    lower    lowering (lower.cpp)   same tree (does nothing this week)
    check    resolver               nothing if OK (exit 0), or an error
    cpp      codegen (codegen.cpp)  the generated C++ source text
    build    g++                    makes an .exe but does not run it
    run      g++ + run              the program's actual output

Keep a copy of the generated output:
    .\build\minic.exe cpp   w03\w03_hello.mini -o build\hello.cpp
    .\build\minic.exe build w03\w03_hello.mini -o build\hello
    .\build\hello.exe

Exit codes:
    0   success
    1   compiler error - the label says which phase failed
        (lex / parse / resolve / codegen / backend / runtime)
    2   wrong command or arguments
    70  internal crash

5. CHECK_PROJECT.py (automatic grader)
--------------------------------------
Runs 10 checks on inputs/ and compares exit code, stdout and stderr
with checks/CASES.json. It does NOT look at w03/ files.

    python CHECK_PROJECT.py --mode start    --compiler .\build\minic.exe
    python CHECK_PROJECT.py --mode solution --compiler .\build\minic.exe

    --mode start     = untouched project fails the expected way (TODO error).
                       10/10 here does NOT mean you are done.
    --mode solution  = your finished code works. 10/10 = done.

"changed fixture" error = a file in inputs/ changed (often line endings).
Fixed for this repo with:  git config core.autocrlf input

8. HOW IT ALL FITS
------------------
Pipeline:  source.cpp -> lexer.cpp (tokens) -> parser.cpp (AST)
           -> lower.cpp -> resolver.cpp -> codegen.cpp (C++ text)
           -> g++ (HostCompiler) -> native .exe

Three languages, three roles:
    Mini  = SOURCE language          (what you write in .mini files)
    C++   = IMPLEMENTATION language  (what minic itself is written in)
    C++   = TARGET language          (what minic generates)

Mini is its own language because it has its own syntax and rules
(fun main(), print, nil, values typed at runtime). Translating to C++ is
just an implementation choice - like Cfront (C++ -> C) or TypeScript -> JS.
Recognising a token (e.g. FOR, PLUS) does NOT mean the parser supports it.
