WEEK 07 — Expression precedence and left associativity

This exercise builds on expression theory.

Complete the task in your starting project. When the solution is provided,
use it to compare your implementation after making your own attempt.
This assignment describes the same exercise in both versions.

GOAL AND LECTURE CONNECTION

Complete two connected parts of a recursive-descent expression parser. Connect
grammar and syntax trees to the way C++ functions consume tokens: an additive
loop builds left association, while unary recursion nests prefix operators.
Multiplication must bind more tightly than addition and subtraction. Repeated
subtraction must build a left-associated tree: (10 - 3) - 2, giving 5.
The parser constructs this tree; generated code and the runtime later compute
its value. Do not calculate the answer inside the parser.

STARTING POINT AND PROVIDED INFRASTRUCTURE

Your starting project already includes variables, assignments and block scopes.
The lexer, AST nodes, other precedence levels, resolver, expression code
generator and runtime are ready to use.
The supplied factor() parses multiplication. Comparisons, equality and
short-circuit and/or are already implemented. Unary AST nodes and their
later-phase support are supplied, but unary - and ! parsing is your task.
Short-circuit execution belongs to the supplied generator, not to term().
The missing parts are the binary +/- loop in Parser::term() and the prefix
operator branch in Parser::unary(). Other inputs pass through these levels.
Only fun main() is supported here; general functions and calls come later.
There are no if/for statements yet. Division is unavailable, and + accepts
only two numbers. The lexer's token set and general --help text do not promise
that this checkpoint supports every feature of the final language.

YOUR C++ TASK

File: src/parser.cpp
Functions: Parser::term() and Parser::unary()
Find: TODO WEEK07: implement addition and subtraction parsing
      TODO WEEK07: implement unary operator parsing

Part 1: additive loop in term()

1. Keep the first call to factor() and store its tree as the current left side.
2. Replace the single TODO guard with repetition while the next token is Plus
   or Minus. Stop without consuming the first token from another grammar level.
3. Consume the operator with advance(). Select BinaryOperator::Add for Plus
   and BinaryOperator::Subtract for Minus.
4. Read the right operand with factor(), not term() or expression(). This
   leaves multiplication inside an operand and avoids right-associative -.
5. Use binaryExpression to make a new tree from the current left tree, the
   selected operator and the right tree. Transfer the operand trees with
   std::move and make the new tree the current left side.
6. Repeat for another + or -. Return the accumulated left tree when finished.
   Remove the placeholder throw; simply deleting the throw is not a solution.

Part 2: recursive prefix branch in unary()

7. If the next token is Bang or Minus, consume it with advance(). Select
   UnaryOperator::LogicalNot for Bang or UnaryOperator::Negate for Minus.
8. Parse the operand with unary(), so --3 and !!true nest correctly. Do not
   call expression(): a prefix operator must not absorb an additive suffix.
9. Form a span from the operator token through the returned operand. Return
   an Expression containing a UnaryExpression with that operation and an
   owned child created with std::make_unique and std::move.
10. Keep the existing return primary() when there is no prefix operator.
    Remove both TODO throws and their completed comments.

Keep factor(), binaryExpression(), the other precedence functions and runtime
unchanged. The binary helper supplies spans and owns both children. In the
unary branch you construct its single owned child and span yourself. Keep the
provided function signatures and pass-through statements.
A single if cannot consume an additive chain. A single primary() operand
cannot consume repeated unary prefixes. Neither algorithm evaluates a value.
